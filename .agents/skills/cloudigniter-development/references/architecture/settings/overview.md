# Settings

Use this reference for settings registry, persistence, route selection, management, or preference changes.

- Core owns `CiSettingsRegistryEntry`, `CiSettingsGroup`, `CiRequestSettings`, the guarded manager, and preference resolution. AWS owns DynamoDB storage and independently authorized AppSync handlers. Next.js composes transport; UI owns `CiSettingsManager`. Template files remain thin bindings.
- Application extensions belong in `src/custom/settings/ci-settings-registry.ts`. Register scope, defaults, strict schema, form fields, metadata, optional cookie mapping, and optional `alwaysLoad`. Reject core ID collisions.
- Follow the established Dashboard/Security presentation: use `CiNextDashboardOverview` for the landing cards, the shared internal UI `CiManagementHeader` for category forms and tables, and the template's breadcrumb children with `withBreadcrumbChildrenMenu`. Derive overview counts from registry metadata, and register every built-in `ci:` card icon in Core rather than relying on an unresolved name.
- Public reads permit anonymous users. Private reads require authentication. Public/Private management uses `ciCanManageSettings` for the selected target. System grants permit Settings-specific cross-tenant administration only when the target has no explicit deny/read-only restriction; do not change the scope engine or propagate provider group assignments. Personal (`user`) reads/writes bind the owner to the session; never accept a caller-selected user ID, including from an administrator.
- Routes select `settings?: readonly string[]`. Load those IDs plus `alwaysLoad` groups only. Missing/empty selection means always-loaded groups only; unknown IDs fail. Maintain Resource Studio UI, normalization, descriptors, actions, generated route maps, runtime guards, and Dev Beacon when changing this contract.
- Values belong in server-built `CiNextContext.settings`, never in proxy context headers/cookies. Keep the loader request-cached and independent of appBootstrap/next-intl to avoid recursion. Cookies override request defaults, not stored records; blank Personal preferences inherit Public defaults. Browser values are not authorization proof.
- Keep category tables storage-only; disabled direct CRUD/subscriptions leave all reads/writes behind guarded operations. Backend saves validate independently, strongly read authorization state, and use conditional revisions. No scans, cross-owner listing, or secrets. Public/Private settings have independent System, GLOBAL, and tenant records; Personal remains account-wide.
- Keys: Public/Private PK `CI#SETTINGS#SYSTEM#PUBLIC|PRIVATE`, `CI#SETTINGS#GLOBAL#PUBLIC|PRIVATE`, or `CI#SETTINGS#TENANT#<id>#PUBLIC|PRIVATE`; Personal PK `CI#SETTINGS#USER#<subject>`; SK `CI#GROUP#<id>`. Use Core builders and exact-key tests. Missing System/Personal groups return defaults without writes. Missing tenant groups copy System once, only on first use, using a source-revision condition and create-only transaction. Never reseed existing tenant copies on ordinary System edits.
- Keep update permission separate from storage readiness. Missing generated Settings operations permit defaults and authorized draft edits before deployment; show a visible disabled Save with `saveUnavailableReason`, and retain the unprovisioned manager's write rejection. Never swallow provider failures after deployment or report a successful save without persistence. Drafts are not an offline queue. Deploy custom registry changes with the backend.
- Validate defaults, cookie precedence, request selection, owner spoofing, authorization deny/allow, schemas, optimistic conflicts, package exports, manifests/IAM, route generation, and request-context transport. Update Users, API, and Developers guides together.

- My Preferences is the UI name for the `user` category; retain `/account/settings`. Its menu starts the loader and captures the previous path in `returnTo`. `CiNextSettingsManager` owns Close navigation, validates a same-origin return path, and falls back to Dashboard; UI confirms discarding unsaved changes only.
- Use one Smart Form and one Save per category. Authorized users start with editable fields and visible Save. Keep inactive sections mounted, namespace field names and conditional references, preserve non-field/immutable values, and reveal invalid sections with `onValidationErrors`. JSON previews the current draft with form actions still visible. Switching sections retains drafts; Cancel discards all edits and returns to view mode. The UI callback is `onSave(updates, target?)` returning `{ ok: true, groups }` or `{ ok: false, message }`.
- Core `saveAll` validates all groups before atomic `store.setMany`; reject mixed categories, duplicate IDs, invalid schemas/revisions, and unsupported adapters. AWS SetSettings accepts `{ target?, groups: [{ id, value, revision, systemRevision?, enforcement? }] }`, repeats authorization, and performs one conditional transaction (up to 100 System/Personal groups or 50 GLOBAL/tenant groups). Tenant writes also condition-check every System revision. Keep single-group saves compatible, never fall back to sequential writes, document transaction cost, and deploy the batch handler before the UI.

See the contributor guide `docs/company-developers/architecture/settings.mdx` for storage, consistency, costs, migration, and observability decisions.

- Choose the request's Public/Private target from trusted resolved tenant context. Keep route-selected/`alwaysLoad` loading and the request snapshot shape unchanged; no eager loading of all tenant groups. Private reads still require authentication, while management evaluates target permissions.
- Store enforcement rules on System groups. `fields: "*"` covers all known top-level fields; `targets: "*"` includes GLOBAL and future tenants. Overlay effective values on read, expose locked fields to forms, and preserve the previous local values during tenant saves so removing enforcement restores them. Reject locked-field tampering and stale System revisions. Rules are returned only to authorized management reads.
- `enforce` and `overwrite` are separate actions on `platform.settings`; only System authorization can grant either. Ordinary update permission must not change policy. One-time overwrite copies saved selected System fields into local records, preserving unselected fields and rules; it intentionally changes the values restored later. Require confirmation and source revisions. One target is atomic, all-target operations enumerate every discovery page first and report per-target failures.
- Reuse the System table's active-tenant GSI1 for paginated discovery only. Strongly validate each selected tenant's base record; reject suspended/deleted/unknown tenants and the System tenant as an ordinary target. Limit IAM to base-table Get, exact-index Query, and category-table Put/ConditionCheckItem where needed. Document first-read writes, transaction cost, and per-target overwrite limits.
- Existing persisted catalogs require an audited core override to add new settings actions/scope kinds and appropriate administrator privilege scopes; changing the default definition does not migrate stored authorization policy. Keep unsupported catalogs fail-closed. Deploy backend/IAM before the tenant UI; never silently replace a customized catalog.
- Regression-test cross-tenant isolation, concurrent initialization, all/selected enforcement, restoration after removal, explicit scoped deny/read-only restrictions on System admins, source/local conflict rollback, bounded discovery, and unchanged Personal ownership. Browser preference cookies continue to override stored defaults.

- Treat Settings access denial as an expected result. Use `ciGetNextAwsSettingsAccess` to distinguish denied read permission (403), explicit session failure (401), and failed/malformed verification (retryable 500); never grant permissions or claim denial on an unverified response. Render the safe `CiErrorBody.errorMeta` through `CiErrorPage` inside the existing `CiPage` shell, with loader-aware recovery navigation in its `actions` slot. Do not throw expected page-access results into the global boundary or expose raw provider details. Keep form drafts when an action or target switch fails.
