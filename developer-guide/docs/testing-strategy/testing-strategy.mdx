## 4. Data Model Behavior in Test/Sandbox

Because all PKs are env‑scoped, you get **transparent separation**:

### Example: Tenant in Live vs Test vs Sandbox

| Mode    | PK                   | SK   |
| ------- | -------------------- | ---- |
| live    | `TENANT#ats`         | META |
| test    | `TENANT#ats#test`    | META |
| sandbox | `TENANT#ats#sandbox` | META |

All your read/write code can keep using common builders:

```ts
const PK = buildTenantPK(tenantId);
// internally calls scopePkWithEnv() based on CI_ENV_MODE
```

This keeps the _application code_ simple, while the **environment‑aware behavior is centralized** in small helpers.

## 5. Amplify Handlers and Env‑Aware Testing

### 5.1 Injecting `CI_ENV_MODE` into Amplify Functions

In `amplify/backend.ts`, export the environment mode and inject it into all
functions that need system table access or testing logic:

```ts
// amplify/backend.ts

const envMode = process.env.CI_ENV_MODE ?? "live";

export const backend = defineBackend({
  // ...
  functions: {
    createTenantHandler: a.function({
      // ...
      environment: {
        CI_SYSTEM_TABLE_NAME: tables.system.name,
        CI_REGION: rt.region,
        CI_ENV_MODE: envMode,
      },
    }),
    // repeat for other handlers...
  },
});
```

Amplify will inject `CI_ENV_MODE` into the Lambda function `process.env`.

---

### 5.2 Typical Pattern Inside a Handler

All handlers that interact with the System table (or could run test‑sensitive operations)
should:

1. Read `CI_ENV_MODE`
2. Use regular key builders (which already call `scopePkWithEnv()`)
3. Optionally guard test‑only actions with `assertNotLive()`

Example: a _generic_ tenant create handler (non‑test specific):

```ts
// @CI/server/handlers/create-tenant.ts
import type { Context } from "aws-lambda";
import type {
  LambdaEvent,
  Response,
  RequestEnvelope,
  CreateTenantInput,
} from "@CI/types";

import { safeParseRequest } from "@CI/utility";
import { err } from "@CI/utility/server";
import { createTenant } from "@CI/server/lib/system/tenants";
import { getEnvMode } from "@CI/env";

export async function createTenantHandler(
  event: LambdaEvent,
  context: Context
): Promise<Response> {
  const tableName = process.env.CI_SYSTEM_TABLE_NAME;
  const region = process.env.CI_REGION;
  const envMode = getEnvMode(); // 'live' | 'test' | 'sandbox'

  if (!tableName || !region) {
    return await err(
      400,
      {
        error:
          "CREATE_TENANT_HANDLER: missing CI_SYSTEM_TABLE_NAME or CI_REGION.",
      },
      {
        message: "missing environment variables",
        parameter: event.arguments.inputString,
        response: "",
        event,
        context,
        env: ["CI_SYSTEM_TABLE_NAME", "CI_REGION", "CI_ENV_MODE"],
      }
    );
  }

  const request = safeParseRequest<RequestEnvelope<CreateTenantInput>>(
    event.arguments.inputString
  );
  if (!request) {
    return await err(
      400,
      {
        error:
          "CREATE_TENANT_HANDLER: invalid inputString (must be Request<CreateTenantInput> JSON).",
      },
      {
        message: "invalid request envelope",
        parameter: event.arguments.inputString,
        response: "",
        event,
        context,
        env: ["CI_SYSTEM_TABLE_NAME", "CI_REGION", "CI_ENV_MODE"],
      }
    );
  }

  const { input, options, scope, action } = request;

  console.log("CREATE_TENANT envMode:", envMode);
  console.log("CREATE_TENANT scope:", scope);
  console.log("CREATE_TENANT action:", action);

  const clientConfig = options?.DynamoDbClientConfig ?? { region };

  let response: Response = await createTenant({
    tableName,
    clientConfig,
    input,
  });

  response = {
    ...response,
    parameter: event.arguments.inputString,
    event,
    context,
    env: ["CI_SYSTEM_TABLE_NAME", "CI_REGION", "CI_ENV_MODE"],
  };

  return response;
}
```

Note:

- **No direct reference to test/sandbox** inside `createTenant` itself.
- It just uses key builders → which use `scopePkWithEnv()` → which read `CI_ENV_MODE`.
- This keeps your business logic clean.

### 5.3 Test‑Only Handlers (Seed/Cleanup)

For handlers that exist _only_ for testing (e.g. `seedTestWorldHandler`, `resetTestTenantHandler`):

- Always call `assertNotLive()` at the top.
- They can call seed helpers and `cleanupEnvironment()`.

Example:

```ts
// @CI/server/handlers/seed-test-world.ts
import type { Context } from "aws-lambda";
import type { LambdaEvent, Response } from "@CI/types";
import { err, ok } from "@CI/utility/server";
import { assertNotLive } from "@CI/env";
import { seedTestTenant } from "@CI/testing/seeds/seed-tenant";

export async function seedTestWorldHandler(
  event: LambdaEvent,
  context: Context
): Promise<Response> {
  try {
    assertNotLive("seedTestWorldHandler is forbidden in live environment.");

    await seedTestTenant("demo");
    // await seedTestRoles('demo');
    // await seedTestOrgUnits('demo');
    // await seedTestSettings('demo');

    return await ok({ message: "Test world seeded." }, { event, context });
  } catch (error: any) {
    return await err(
      500,
      { error: String(error?.message ?? error) },
      { event, context }
    );
  }
}
```

> **Do not** deploy such handlers in live stacks.

## 6. Next.js Client Components and Testing

### 6.1 Exposing Env Mode to Client

Only expose env mode to the client under a **public** prefix:

In `next.config.js`:

```js
// next.config.js
module.exports = {
  env: {
    // For server-side only:
    CI_ENV_MODE: process.env.CI_ENV_MODE,
  },
  webpack(config) {
    return config;
  },
};
```

If you need it on the client (for UI flags), use:

```env
NEXT_PUBLIC_CI_ENV_MODE=live
```

And in code:

```ts
export function getClientEnvMode(): "live" | "test" | "sandbox" {
  const raw = process.env.NEXT_PUBLIC_CI_ENV_MODE ?? "live";
  if (raw === "test" || raw === "sandbox") return raw;
  return "live";
}
```

> **Important:** Client should never be able to **switch** env mode in real deployments;
> it is a build/deploy‑time or server‑side configuration.

---

### 6.2 Gating Test UI in Client Components

Use env mode on the client only to:

- Show/hide dev/test banners
- Show/hide dangerous UI commands (e.g. “Reset Test Data” button)
- Show helpful labels like “SANDBOX MODE” on the top bar

Example:

```tsx
// @CI/ui/components/EnvBadge.tsx
"use client";

import { getClientEnvMode } from "@CI/env/client";

export function EnvBadge() {
  const envMode = getClientEnvMode();
  if (envMode === "live") return null;

  const label = envMode.toUpperCase();
  const color = envMode === "test" ? "bg-yellow-500" : "bg-purple-500";

  return (
    <div
      className={`fixed top-2 right-2 px-3 py-1 text-sm text-white rounded ${color}`}
    >
      {label} MODE
    </div>
  );
}
```

### 6.3 Don’t Expose Test‑Only Actions in Live

If you have a UI that triggers a test‑only handler (e.g. “Seed Demo Data”):

```tsx
"use client";

import { getClientEnvMode } from "@CI/env/client";

export function SeedDemoButton() {
  const envMode = getClientEnvMode();

  if (envMode === "live") {
    // Completely hide or disable this button
    return null;
  }

  const handleClick = async () => {
    await fetch("/api/ci/seed-test-world", { method: "POST" });
  };

  return <button onClick={handleClick}>Seed Demo Data</button>;
}
```

This way:

- In **live**: users never see the button.
- In **test/sandbox**: devs and CI flows can use it safely.

## 7. Typical Testing Workflow

### 7.1 Local / Dev Sandbox

1. Set environment:

   ```bash
   CI_ENV_MODE=sandbox
   ```

2. Run sandbox seed:

   ```bash
   npm run ci:seed:sandbox
   ```

3. Manually play with the app at `http://localhost:3000`.

4. When you’re done:

   ```bash
   npm run ci:cleanup:sandbox
   ```

---

### 7.2 Automated E2E Tests (Cypress / Playwright)

1. Set environment:

   ```bash
   CI_ENV_MODE=test
   ```

2. Seed test world:

   ```bash
   npm run ci:seed:test
   ```

3. Run E2E test suite:

   ```bash
   npm run test:e2e
   ```

4. Cleanup:

   ```bash
   npm run ci:cleanup:test
   ```

Seed scripts can be hosted under `scripts/` or `testing/seeds/` and reused in CI.

## 8. Example Playwright Test Using Seed Helpers

```ts
// tests/e2e/admin-dashboard.spec.ts
import { test, expect } from "@playwright/test";
import { seedTestTenant } from "@CI/testing/seeds/seed-tenant";
import { seedTestRoles } from "@CI/testing/seeds/seed-roles";

test.describe("Admin dashboard", () => {
  test.beforeAll(async () => {
    await seedTestTenant("demo");
    await seedTestRoles("demo");
  });

  test("loads for demo tenant", async ({ page }) => {
    await page.goto("/tenant/demo/login");
    await page.fill("#email", "admin@demo.local");
    await page.click("#login");

    await expect(page.locator("h1")).toHaveText("Demo Tenant Dashboard");
  });
});
```

Because:

- `CI_ENV_MODE=test`
- `seedTestTenant` and `seedTestRoles` are guarded with `assertNotLive()`
- PKs/SKs are scoped via `scopePkWithEnv()`

…you can be confident this **never touches live data.**

## 9. Test “Do & Don’t”

### ✅ DO

- Use `getEnvMode()` instead of reading `process.env.CI_ENV_MODE` everywhere.
- Use `scopePkWithEnv()` for any System Table primary keys.
- Use `assertNotLive()` in any seeder/cleanup utilities and test‑only handlers.
- Keep seeders and cleanup scripts under a clear namespace (`@CI/testing/...`).
- Run `cleanupEnvironment('test')` and/or `cleanupEnvironment('sandbox')` regularly.
- Gate test DevTools UI in client components based on `NEXT_PUBLIC_CI_ENV_MODE`.
- Document your test tenants and roles so everyone uses the same identities in tests.

### ❌ DON’T

- ❌ Don’t run seeders or cleanup scripts without calling `assertNotLive()`.
- ❌ Don’t manually append `#test` or `#sandbox` to PKs — always use `scopePkWithEnv()`.
- ❌ Don’t allow `CI_ENV_MODE=test` or `sandbox` in true production stacks.
- ❌ Don’t mix test and live tenants (e.g., same ID but manually inserted).
- ❌ Don’t bypass environment helpers by directly accessing raw DynamoDB keys.
- ❌ Don’t expose “reset system”, “seed demo data”, etc., in client UI for live mode.
- ❌ Don’t assume “local = safe” — always enforce environment checks.

## 10. Summary

CloudIgniter’s testing strategy builds on three pillars:

1. **Environment Modes** (`live`, `test`, `sandbox`)
2. **Environment‑Aware Keys** via `scopePkWithEnv()`
3. **Guarded Tools** (`assertNotLive`, seeders, cleanup utilities, env‑aware handlers & UI)

By consistently using the helpers and tools described here, you gain:

- Strong guarantees that live data remains untouched
- Easy, repeatable test setups
- Clean, deterministic teardown after tests
- A standard pattern your whole team can follow

> **Guiding Principle:**  
> _You should be able to run any test script or click any “test” button with full confidence that live tenants and live data are completely safe._

# 6. Cleanup Strategy (Test & Sandbox Only)

CloudIgniter includes an internal utility:

`cleanupEnvironment(envMode: 'test'|'sandbox')`

It deletes:

- Tenants
- OU trees
- Roles
- Role mappings
- Settings

only for that environment.

**Never runs in `live` mode.**
