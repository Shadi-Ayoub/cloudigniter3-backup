CloudIgniter activates Dev Beacon, Debug Probe, and seeder controls only when all of these are true:

1. `CI_ENV_MODE` is `development`;
2. the current user is authenticated;
3. the user's role list contains the exact canonical role ID `developer`.

The same rule runs at the root UI, server action, and provider handler. A hidden button is not the security
boundary.

## Move the Dev Beacon

The configured `position` preset sets the [Dev Beacon](/dictionary/d#dev-beacon) button's initial location. If it
covers a page control, drag the button with a mouse, touch, or pen and release it anywhere else in the viewport.
The button stays fully on-screen, and a small movement threshold prevents an ordinary click from being mistaken
for a drag. Clicking, pressing **Enter**, or pressing **Space** still opens the developer dashboard.

With keyboard focus on the button, press **Alt + Arrow key** to move it in 8-pixel steps. Add **Shift** to move in
32-pixel steps. A dragged location lasts for the current mounted client session; reloading the page, remounting the
component, or changing its `position` prop restores the configured preset.

## Check Org Unit resolution

Open either the **Tenant Resolution** or **Org Unit Resolution** checkup report and select **View JSON Report**
to inspect all tests for that section in one JSON document. Select **Copy JSON** to copy the summary, probe paths,
test messages and states, and expected-versus-actual results for pasting into a troubleshooting tool. A confirmation
appears after copying. If clipboard access is unavailable, select the JSON in the viewer and copy it manually.
Select **View Test Results** to return to the test cards.

The [Dev Beacon](/dictionary/d#dev-beacon) **Org Unit Resolution** report checks active root, deep active,
missing, suspended, and archived [Org Units](/dictionary/o#org-unit). Its reserved probe tenant uses built-in
fixtures, so these checks do not require database seeding. A successful match removes the complete Org Unit
path and leaves `/dashboard`; the missing case retains its original feature pathname. Suspended and archived
nodes resolve with their status so the routing layer can apply its normal status handling.

The internal lookup repeats the developer-access check using the forwarded session cookie. If only the missing
case passes, inspect the lookup response and verify that the request retains the authenticated session and meets
the development-mode and role requirements. Application Org Units continue to use the configured persistence provider;
these diagnostic fixtures do not verify database contents.

## Define a seeder

Application seeder definitions and data live in the custom seam:

```text
apps/template/src/custom/dev/seeder/
├── seeder.config.ts
└── data/
    └── tenants/
        └── tenants.json
```

```ts title="src/custom/dev/seeder/seeder.config.ts"
import type { CiSeederManifest } from "@cloudigniter/core/types";

export const appSeederManifest = {
  version: 1,
  seeders: [
    {
      id: "test-tenants",
      title: "Test Tenants",
      resource: "platform.tenants",
      dataDirectory: "data/tenants",
      dataFiles: ["tenants.json"],
      createApi: "SeedTenants",
      cleanupApi: "CleanupSeededTenants",
    },
  ],
} as const satisfies CiSeederManifest;
```

Operation names are trusted application registry IDs, not arbitrary URLs. The application adapter must allowlist
the supported operation before calling it.

Tenant JSON is an array. Each item requires `tenantId`, `name`, and `slug`; optional fields include `description`,
`status`, `region`, `tenantType`, `usersCount`, `meta`, and a parent-first `orgUnits` array. Each Org Unit requires `orgUnitId`, `name`, `slug`, and one or more `tenantIds`; `parentId`, description, status, and metadata are optional.

```json
[
  {
    "tenantId": "dev-group-hq",
    "name": "Group Headquarters (Test)",
    "slug": "dev-group-hq",
    "status": "active",
    "orgUnits": [
      {
        "orgUnitId": "dev-central-hq",
        "name": "Central Headquarters",
        "slug": "central-hq",
        "tenantIds": ["dev-group-hq", "dev-company-a", "dev-company-b"]
      }
    ]
  }
]
```

`ciReadJsonSeederData()` resolves paths beneath `src/custom/dev/seeder`, rejects traversal and non-JSON files,
enforces a size limit, and requires each file to contain an array. Domain validation still runs before the
provider API is called.

## Seed and clean up tenants

Open **Dashboard → Tenants** as a user with the `developer` role while the application and Amplify backend are in
`development` mode. Select the **Seeder** action in the table toolbar to open the **Test Tenants** dialog. The
**Seed Tenants** action creates tenant and Org Unit fixture records. Re-running it skips records already owned by that seeder and
fails rather than overwriting a tenant with unrelated ownership. The toolbar action and dialog are omitted for
every other role or environment.

**Clean Up** in the Seeder dialog opens a destructive confirmation. Cleanup queries the seeder's marker partition, then conditionally
deletes each matching resource and marker together. Org Units are removed deepest-first with every tenant/path attachment before tenants. It still finds data after a fixture is removed from JSON.
Ownership-mismatched, protected, and malformed records are preserved and reported.

Tenant and Org Unit seed records and markers share the System-table security/lifecycle boundary. Cleanup has no
Cognito participant.

The **Test Users** seeder on **Dashboard → Users** creates three disposable Cognito identities, User
Profiles, groups, and scoped assignments. It writes `extensions.cloudigniterSeeder = "test-users"` and refuses to
adopt or clean up a matching email without that provenance. A profile or assignment failure invokes the account
rollback path; cleanup uses the ordinary soft-delete and purge lifecycle. User fixture addresses and extensions
remain JSON objects—the AWS adapter owns AppSync `AWSJSON` wire serialization.

### Troubleshoot transactional permission errors

Creating an Org Unit conditionally verifies its tenant and predecessor records inside the same DynamoDB transaction.
The deployed seed-tenants Lambda role therefore needs `dynamodb:TransactWriteItems` plus the component actions
`dynamodb:ConditionCheckItem`, `dynamodb:PutItem`, and `dynamodb:UpdateItem` on the System table. If the Seeder
reports that one of these actions is not authorized, verify the target deployment and the Lambda role’s policy
for that table. Apply the required grants through the backend configuration and deploy them to the intended
development environment before retrying. Same-seeder tenant and Org Unit records from a partial run are skipped
safely.

## Run seeders through the application

Run seeders from the authenticated application UI. Server actions and provider handlers verify the application
actor, environment, and role before accessing fixture data. Local AWS credentials alone do not authorize an
application seeding operation.

See [`ciCanAccessDeveloperTools`](../api-reference/shared-apis/ci-can-access-developer-tools),
[`ciReadJsonSeederData`](../api-reference/server-apis/ci-read-json-seeder-data), and
[seeder types](../api-reference/type-definitions/CiSeederTypes).
