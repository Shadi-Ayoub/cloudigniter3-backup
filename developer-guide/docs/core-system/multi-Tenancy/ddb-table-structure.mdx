# DynamoDB Table Structure

CloudIgniter uses one table per security and operational bounded context. The `System` table uses single-table
modeling for related control-plane entities; it is not a shared table for every CloudIgniter capability.

Authorization roles, privileges, and assignments remain in the dedicated `EmberguardAccess` table. User
profiles and data with different public/private access, lifecycle, throughput, stream, or restore requirements
remain in their appropriate boundaries. See the
[DynamoDB bounded-context strategy](/company-developers/persistence/dynamodb-strategy).

### System Table Overview

Example table name: `System`

The table stores related control-plane records such as:

- Tenants
- Org Units
- tenant/Org Unit relationships
- system metadata with the same administrative and operational boundary

Do not add roles, permissions, public settings, profiles, or sustained audit events to this table merely to
reduce table count.

### Tenant Item Shape

A tenant is stored as a single DynamoDB item.

**Primary Keys**

```text
PK = CI#SYSTEM#TENANT#<tenantId>
SK = CI#META
```

```json title="Example Item"
{
  "PK": "CI#SYSTEM#TENANT#school-abu-dhabi",
  "SK": "CI#META",
  "id": "school-abu-dhabi",
  "type": "TENANT",
  "status": "active",
  "name": "School Abu Dhabi",
  "slug": "abu-dhabi",
  "description": "Main Abu Dhabi campus",
  "meta": {
    "region": "AD",
    "country": "AE",
    "timezone": "Asia/Dubai",
    "orgUnitsCount": 12,
    "capacity": 1800,
    "tags": ["urban", "flagship"]
  },
  "createdAt": "2024-01-15T08:30:00.000Z",
  "updatedAt": "2024-01-15T08:30:00.000Z"
}
```

### Access Patterns

| Use Case             | Key Pattern                                                      |
| -------------------- | ---------------------------------------------------------------- |
| Get tenant by ID     | Exact `PK = CI#SYSTEM#TENANT#<id>` and `SK = CI#META`            |
| List tenants         | A named, paginated tenant-list index or materialized collection  |
| Update tenant status | Exact key plus a condition on the current version or state       |
| Audit/tracing        | A separate audit/event boundary when retention or volume differs |

Never implement tenant listing with a request-path table scan. Define the access pattern and index projection
before adding the index, including its storage and write-amplification cost.

All PK, SK, and index keys must use the public core table-key helpers described in the
[CloudIgniter table-key convention](/docs/library/dynamodb/table-key-convention).
