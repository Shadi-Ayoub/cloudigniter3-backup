  questions:
    - question: "Why does test mode deny deployed developer tools even when tests need fixtures?"
      answer: "Test mode supports controlled automated execution, not access to deployed development mutations. Supply explicit fixtures to focused tests or use an authorized development deployment for those integration operations; deployed developer tools still require development mode and the trusted actor checks."
    - question: "Does naming a deployment sandbox introduce another accepted CiEnvMode value?"
      answer: "No. CiEnvMode accepts only development, test, staging, and production. Sandbox names a deployment or resource target, so configure that target with an accepted runtime mode and continue enforcing the corresponding capability rules."

```ts
export type CiEnvMode =
  | "development"
  | "test"
  | "staging"
  | "production";
```

| Mode | Purpose | Developer tools |
| --- | --- | --- |
| `development` | Local or explicitly disposable application development | Eligible after authentication and exact `developer` role checks |
| `test` | Automated test execution | Denied |
| `staging` | Production-like validation | Denied |
| `production` | Live application operation | Denied |

`test` is deliberately not a developer-tools bypass. Tests should invoke focused functions with explicit test
fixtures or exercise a development deployment; they must not make deployed mutation handlers broadly available.

Use these exact values in environment files and application configuration. A deployment label such as
“sandbox” does not change the accepted `CiEnvMode` values.
