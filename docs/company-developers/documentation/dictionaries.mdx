CloudIgniter Docs has a public **Users** surface and an extended **Developers** surface on the same `docs.cloudigniter.io` website. Company pages, the Developer Dictionary, private command manuals and Skills are delivered only to authenticated users with the exact `developer` role and allowed EmberGuard access. The website supplies the CloudIgniter template authentication session; Docs uses no separate account system. Both dictionaries remain visible in the local maintainer preview.

| Dictionary | Audience | Content | Appearance |
| --- | --- | --- | --- |
| [Dictionary](/dictionary) | CloudIgniter users building applications | Shared platform and supported ecosystem concepts | Blue |
| [Developer Dictionary](/developer-dictionary) | CloudIgniter company developers | Package internals, contributor workflows, and implementation technologies | Green |

Both tools provide alphabet browsing, term search, linked definitions, and full-page navigation. The developer edition keeps the user dictionary available as its foundation. Do not copy a shared definition into the developer dictionary simply to make it available to company developers.

The navbar's **Dictionary** dropdown contains two rows: **Dictionary** and **Developer Dictionary**.
Each row has a book icon that opens that audience's viewer and a label linking to its full dictionary page.
The same dropdown is available in the mobile navigation menu, with separate viewer and page controls.
While either viewer is open, the page behind it is frozen. Its term list and
definition remain independently scrollable. Dismissing the viewer restores page
scrolling at the same position.

The profile definitions [CloudIgniter User](/developer-dictionary/c#cloudigniter-users)
and [CloudIgniter Developer](/developer-dictionary/c#cloudigniter-developers) belong
in the Developer Dictionary. Their singular and plural names open the same green
viewer entries; neither definition is included in the user dictionary.

## Add a definition

1. Choose the audience. Internal terminology such as DEV Toolkit, API Facade, and Staged Archive belongs in the developer dictionary.
2. Add a concise definition beneath a level-two heading in the appropriate letter MDX file in `docs/dictionary` or `docs/developer-dictionary`. Give developer headings explicit stable anchors.
3. Add the same term and anchor to `dictionary-terms.ts` or `developer-dictionary-terms.ts`. Those catalogs drive the sidebar, viewer search, and automatic linking. An optional third tuple item lists aliases, such as `["CloudIgniter User", "cloudigniter-users", ["CloudIgniter Users"]]`; aliases share one definition and one viewer result.
4. When adding a previously unused letter, register its lazy page import in `src/components/DictionaryViewer/developer-dictionaries.ts` (or `dictionaries.ts` for a user term). Link it from the dictionary index.
5. Link a focused guide for the full workflow. Run the dictionary tests, date update/check, typecheck, and production build.

The shared viewer renders the same MDX definitions as the full pages. Each dictionary keeps its own results and green/blue styling; one dialog handles both tools so following a shared-term link does not stack dialogs.

## Linking and search

The user dictionary linker runs in public guides and API Reference pages. Company developer pages use both catalogs; dev command manuals add internal terms too. Existing links, headings, code, and dictionary definitions retain their authored content. Use canonical definition URLs for explicit links, such as `/developer-dictionary/d#dev-toolkit`.

Both dictionaries are excluded from the general guide search index. Each Dictionary Viewer searches only its own term catalog. Dates apply to both dictionaries; article feedback is omitted from both.

Automatic linking prefers the longest complete term or alias and recognizes phrases
across whitespace and source line breaks. Both singular and plural profile names
link as complete phrases to their shared definition. Viewer search accepts aliases
while displaying the canonical name. Preserve stable definition anchors when
changing a display name so existing links continue to open the same definition.

### Match the meaning in context

A word should open a definition only when the sentence uses its defined technical
meaning. In source-mirroring guidance, an **approval claim** is an assertion about
approval. The Dictionary's **Claim** entry describes a statement carried in an
authentication token. Those uses have different meanings, so the approval wording
remains plain text.

For an ambiguous label, the catalog's optional fourth tuple item disables automatic
linking of that bare label while retaining qualified aliases:

```ts
["Claim", "claim", ["Token Claim", "Token Claims"], { autoLinkLabel: false }]
```

The viewer still lists and searches **Claim**. Phrases such as **token claim** and
**identity claim** link automatically. Where the authentication context is already
clear, an author can explicitly link the bare word with
`[claim](/dictionary/c#claim)`. An entry without aliases and with
`autoLinkLabel: false` requires explicit links for every occurrence.

Choose aliases by meaning, not spelling alone. When a word has several technical
senses, use qualified definition names and separate anchors. Check related pages
for both legitimate links and false matches, including ordinary verbs, and run
the dictionary regression tests before publishing the guide.

## Publishing boundary

`pnpm --filter docs build:hosting` builds public and developer bundles. The public
build omits internal plugins, the Developer Dictionary module/catalog/MDX chunks,
private command manuals, skill sources, internal search records and private
page-date metadata. Public navigation offers only its permitted tools. A compiler
check prevents company source from entering its bundle.

The extended guide keeps both dictionaries under `/developers/`, including its
HTML, JavaScript, search and static assets. CloudFront validates a short-lived
delivery grant before serving any of those bytes. The CloudIgniter website issues
the grant only after verifying its authenticated identity, exact developer role
and EmberGuard `documentation.company/read` decision. Hidden links and browser
role flags are presentation, never authorization evidence.

The local preview includes both audiences without production enforcement. The
website runtime integration and AWS setup are still required; the combined
preview is not a deployable public payload. Follow
[Publish CloudIgniter Docs](/company-developers/publishing/docs).
