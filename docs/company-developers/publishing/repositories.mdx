## One workspace, several delivery destinations

The **integration workspace** is the complete private CloudIgniter monorepo. It contains `packages/`, `apps/templates/cloudigniter-next-aws-v1/`, `docs/`, shared configuration, the lockfile and Changesets. It is the normal place to develop and validate changes.

The publication layout uses a **pair of repositories per product**. A private source repository holds the package/template/Docs source selected from the workspace, or independent website source maintained directly in its own checkout. Its build repository holds reviewed output ready for delivery. The release policy calls this layout `topology: "paired"`: “topology” means repository arrangement, and “paired” means a separate source and build destination. It does not mean that developers work inside nested Git repositories.

All unqualified names in this table are under `cloudigniter-io/`. JODARIS uses the explicit `jodaris/` owner. Every source and build repository is private; only the exported application template is public.

| Project | Private source | Build or export | Delivery |
| --- | --- | --- | --- |
| `@cloudigniter/aws` | `cloudigniter-aws` | `build-cloudigniter-aws` | Public npm |
| `@cloudigniter/cli` | `cloudigniter-cli` | `build-cloudigniter-cli` | Public npm |
| `@cloudigniter/core` | `cloudigniter-core` | `build-cloudigniter-core` | Public npm |
| `@cloudigniter/dev` | `cloudigniter-dev` | `build-cloudigniter-dev` | Restricted npm |
| `@cloudigniter/emberguard` | `cloudigniter-emberguard` | `build-cloudigniter-emberguard` | Public npm |
| `@cloudigniter/next` | `cloudigniter-next` | `build-cloudigniter-next` | Public npm |
| `@cloudigniter/ui` | `cloudigniter-ui` | `build-cloudigniter-ui` | Public npm |
| CloudIgniter Docs | `cloudigniter-docs` | `build-cloudigniter-docs` | AWS website |
| Next/AWS template | `source-cloudigniter-next-aws-v1` | `cloudigniter-next-aws-v1` | Public GitHub template |
| CloudIgniter website | `cloudigniter-website` | `build-cloudigniter-website` | Independent AWS website |
| JODARIS website | `jodaris/jodaris-website` | `jodaris/build-jodaris-website` | Independent AWS website |

The canonical full-workspace repository is `cloudigniter-io/cloudigniter`, configured separately as `workspaceRepository` in `github-policy.json`. Company `main` enforces the reviewed integration workflow. This name can be changed there without renaming the local folder or altering the package pairs. See the [monorepo PR strategy](./monorepo-pull-requests).

The private and public template names are deliberately distinct. The former `cloud-igniter/cloudigniter-v1` destination has been replaced. The existing private `Shadi-Ayoub/cloudigniter3-backup` remote remains the integration-workspace backup; the developer toolkit does not infer release destinations from it or push its history to product repositories.

:::warning Build from the complete workspace
The monorepo remains the local build/integration workspace, including shared configuration, Changesets and dependency checks. Separate source clones are useful for inspection and normal Git development, but are not promised to build alone: several current package configurations require sibling packages and template files. This change does not split the developer's working tree into nested Git repositories.
:::

## How .cloudigniter is created

A leading dot is a Unix convention for hiding a file or directory in ordinary listings. It says nothing about whether the contents are generated. The repository’s root `.cloudigniter/` directory is **maintained source configuration**, created and committed as part of the toolkit’s setup. Cloning the complete workspace brings it with the rest of the tracked files. There is no `dev init` command that reconstructs these policies.

Administrators edit these JSON files through reviewed monorepo PRs. The toolkit reads and validates them; it does not silently regenerate them from Git remotes. Missing or invalid policy produces an error. Keep usernames, destinations and non-secret settings here; keep credentials in their respective credential stores and service settings.

| File or folder | Maintained contents and reader |
| --- | --- |
| `github-profiles.json` | Profile names such as `developer` and `approver`, each with a real GitHub username and role. Commands use it to select a stored credential. |
| `github-policy.json` | Authorized requesters, separate backup and full-workspace destinations, private template request repository, public template destination and template reviewers. |
| `repositories.json` | Project IDs, local source paths, source/build destinations, visibility and delivery type. Repository, scaffold and release commands use it. |
| `release-policy.json` | Package paths, npm access, allowed tags, registry, reviewers, base branch and repository arrangement. |
| `template-policy.json` | Explicit exported file inventory, dependency versions, scripts, overlays and text replacements. An overlay is a maintained file copied into the export to replace a workspace-specific file. |
| `template/` | Those standalone overlay files, including the README, TypeScript configuration, pnpm configuration and example data. These are reviewed inputs, not a build cache. |

:::note Repository inventory
`.cloudigniter/repositories.json` is the routing inventory. Packages map to their current `packages/*` directories, the guide to `docs`, and the template to `apps/templates/cloudigniter-next-aws-v1`. Template export still accepts any configured source below `apps`. The two independent websites have `sourcePath: null` because their source is outside the monorepo. They have their own checkouts, review, CI and AWS delivery. Workspace cloning and source mirroring never download or synchronize them. GitHub repository permissions determine which developers can clone each website.

Docs selects `staticAccess: "cloudigniter-developer"`: public documentation and protected company material share `docs.cloudigniter.io`, using template authentication and EmberGuard. Its build repository requires separated static output; see [Docs publishing](./docs).

Docs uses the project ID `cloudigniter-docs` in DEV commands and Publisher metadata. Its local folder and pnpm package are `docs`; the GitHub destinations are `cloudigniter-io/cloudigniter-docs` and `cloudigniter-io/build-cloudigniter-docs`.
:::

In paired mode, `release-policy.repository` is `null` because there is no single npm publication repository. Each package’s build repository is its npm publisher. This does not prevent a full-monorepo review repository: `github-policy.workspaceRepository` supplies that separate destination.

## Read configuration through dev

```bash
dev github profiles
dev github repositories
```

The first command prints the non-secret account profiles. The second prints the project inventory, including the exact organization paths that subsequent commands will use. Both are offline reads; neither logs in or creates a repository. Review their output after any organization rename or repository transfer.

Generated files appear in explicitly selected output directories, such as `../build-core-setup`, and in release request/artifact records. They are described in [Generated files and workflows](./generated-files); do not confuse them with the maintained root policy directory.

## Downstream source updates

Approved monorepo merges synchronize [mapped private source roots](./strategy/source-mirroring#which-repositories-receive-source). JODARIS and CloudIgniter Website are excluded because they have no workspace source path. Config TS remains shared monorepo source. Source mirrors preserve independent history and require their own App access; the backup remote and build/public destinations are outside this synchronization.

## Independent website access

Clone/pull the complete monorepo for connected packages, templates, Docs and shared
policy. Grant the two websites separately; access to the workspace grants neither
website source access nor production access. From the workspace root, explicitly
select a website with `dev github clone <project> --output=<external-checkout>` or
update its clean base branch with `dev github pull`. Build checkouts are selected
separately with `--repository-kind=build`. These commands never fetch both sites as
a side effect. See [website delivery](./websites).

## Existing history and first imports

Removing the website directories changes the current monorepo tree. Earlier
monorepo commits still contain their source, and readers with access to that
history can retrieve it. If website access must also exclude historical source,
use an owner-reviewed clean-history migration before granting new developer
access. Rewriting shared history or replacing the canonical repository is a
separate operation; deleting the current folders does not perform it.

Relocated local website sources are preserved for an initial source-repository
import. Review their complete source tree and CI in a source PR; do not copy the
monorepo Git history into either website. The standalone build scaffolds are
reviewable local setup files until committed and pushed to their build repos.
