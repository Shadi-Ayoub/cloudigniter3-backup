## The website delivery contract

CloudIgniter Docs is a static website with public and authenticated company-developer material at `docs.cloudigniter.io`. It stays in the monorepo, uses CloudIgniter template authentication and EmberGuard, and has its own protected output workflow. Follow [Publish CloudIgniter Docs](./docs) for its build, access policy and AWS configuration. The unrestricted `site/index.html` workflow below applies to the two marketing websites.

The [publishing map](./strategy/#publishing-map) shows the independent website
path and the shared-authentication connection between CloudIgniter and Docs.

The formal websites are independent private source/build pairs:

| Website | Source repository | Reviewed AWS output repository |
| --- | --- | --- |
| CloudIgniter (`cloudigniter.io`) | `cloudigniter-io/cloudigniter-website` | `cloudigniter-io/build-cloudigniter-website` |
| JODARIS | `jodaris/jodaris-website` | `jodaris/build-jodaris-website` |

Both have `sourcePath: null` in the workspace inventory. This marks source maintained
outside the monorepo, rather than absent source. The current websites are static
HTML applications. Repository permissions and an explicit clone control developer
access; a workspace clone/pull includes packages, templates, Docs and shared files,
but neither website. These sites have no source-mirroring step.

## Select a website checkout

From the monorepo root, clone only the site you are authorized to maintain:

```bash
dev github clone cloudigniter-website --output=../websites/cloudigniter-website --profile=developer
dev github clone jodaris-website --output=../websites/jodaris-website --profile=developer
```

Each command is an independent action. The external output must not exist before
clone. For an existing clean `main` checkout, use `dev github pull` with the same
project and output; it verifies the exact HTTPS origin and updates by fast-forward.
Select the corresponding output repository separately with `--repository-kind=build`.

Develop source directly in that site's checkout. Push a source feature branch and
open `dev github pr create --project=<website-id> --repository-kind=source` from the
monorepo to request source review. The website's own `website-quality.yml` validates
and stages public output, without AWS credentials or a monorepo checkout. Protect
its source branch with that check and independent review. Grant developer access
per source repository and grant output/deployment access separately.

The static scaffold supports both formal websites because they currently stage `dist/index.html`. Server rendering needs an explicit runtime such as Amplify Hosting or a container service. Uploading Next.js `.next` output to S3 does not supply that runtime.

## Generate and install the deployment scaffold

```bash
dev github scaffold cloudigniter-website --hosting=static --output=../build-cloudigniter-setup
dev github scaffold jodaris-website --hosting=static --output=../build-jodaris-setup
```

The project ID selects the guide’s configured source/build pair. `--hosting=static` confirms the static output contract. The new external output contains a README, Code Owners and `deploy-aws.yml`, explained in [Generated files and workflows](./generated-files#website-scaffold-files).

The approver reviews and commits those files at the build repository root, then configures its protected `main` branch and `production` environment. The scaffold itself creates no GitHub or AWS resources.

## Request website output review

Build and check the selected marketing website in its independent source checkout,
then copy its `dist/` contents into `site/` of the matching build checkout. Record
the exact source commit, CI results and artifact hash. Commit a feature branch,
push it and request output review with that website's project ID:

```bash
dev github pr create --project=cloudigniter-website --repository-kind=build \
  --head=website/update --title="Update the CloudIgniter website" \
  --body-file=/tmp/website-build-pr.md --profile=developer
```

The branch and description file must already exist. Review and merge through the
[standard PR commands](./github-commands), retaining `--repository-kind=build`.
For Docs, use the separated `build:hosting` payload and [protected workflow](./docs).

## Configure AWS once per website

An AWS administrator provisions a private S3 bucket, CloudFront distribution, bucket access for that distribution, and the required DNS/TLS configuration. Use one deliberate hosting design per site; the generated workflow does not choose resources.

Create an AWS IAM role trusted by GitHub OIDC. Scope its trust to the exact repository and `production` environment and the `sts.amazonaws.com` audience. Use the actual GitHub subject format for that repository, including immutable owner/repository IDs where the current [claim](/dictionary/c#claim) format requires them. Do not copy a guessed subject from another repository.

Limit role permissions to the intended bucket’s listing/read/upload operations and the specific distribution’s invalidation. See the official [AWS credentials action and OIDC setup](https://github.com/aws-actions/configure-aws-credentials) and [GitHub’s AWS OIDC guide](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).

Configure these **environment variables** in the build repository’s `production` environment:

| Variable | Purpose |
| --- | --- |
| `AWS_ROLE_ARN` | The IAM role GitHub may assume. |
| `AWS_REGION` | Region used by AWS commands. |
| `SITE_BUCKET` | Bucket name that receives `site/` contents. |
| `CLOUDFRONT_DISTRIBUTION_ID` | Distribution whose cache is invalidated after upload. |

These are resource identifiers, not AWS access keys. The job receives temporary credentials through OIDC. Restrict environment deployments to protected `main` and apply the [available GitHub controls](./github-setup#actions-and-production-credentials).

## Deploy the reviewed commit

As `jodaris`, open **Actions → Deploy reviewed static website → Run workflow** in the build repository and select `main` after the output PR is merged.

The job checks the exact repository, protected branch, original/rerun approver, required settings and `site/index.html`. It rejects symlinks, assumes the AWS role, syncs the committed static files and invalidates CloudFront. It does not rebuild with production credentials.

```bash
dev github run list --project=cloudigniter-website --repository-kind=build --profile=approver
dev github run view --project=cloudigniter-website --repository-kind=build \
  --run-id=123456789 --profile=approver
```

The first command lists recent deployment runs; replace the example ID in the second with the actual run to inspect its jobs and result. Verify the hosted page after a successful run.

## Retention and recovery

The generated S3 sync does not delete old objects. Decide cache headers, retention, removal of retired files and rollback as explicit hosting operations. A failed upload can leave partial website updates; do not assume deployment is atomic. Keep the last known good reviewed build and redeploy it through the approved process when needed.

## Build and preview the formal websites

Run the website's check and build inside its standalone source checkout:

```bash
# CloudIgniter website checkout
node scripts/check.mjs
node scripts/prepare-static-deploy.mjs

# JODARIS website checkout
node scripts/check.mjs
bash scripts/prepare-static-deploy.sh
```

Both builds stage only public output in `dist/`. Copy the contents into `site/` of
the selected build checkout and open an output-review PR with that website project
ID and `--repository-kind=build`. Record the exact source commit, CI result and
artifact hash in the PR. Merge and dispatch the build repository's `deploy-aws.yml`
only after AWS resources, OIDC and the production variables are configured. AWS
hosting is a future setup step; local build/scaffold generation does not deploy.

From the monorepo root, explicitly select a downloaded website for local preview:

```bash
dev start website cloudigniter --site-root=../websites/cloudigniter-website
dev start website jodaris --site-root=../websites/jodaris-website
dev open terminal cloudigniter --site-root=../websites/cloudigniter-website --external
```

Use an absolute checkout path when invoking from a nested monorepo directory.
Production preview adds `--mode=prod` and requires a prepared `dist/`. Metadata
must identify the selected website. Workspace Publisher does not discover or edit
these external repositories.

A future Next.js migration consumes the exported template and released packages
in the website's own repository. Preserve separate access and review; do not add
it to monorepo source mirrors or use `workspace:*` dependencies there. Provide
`dev`/`start` scripts and update the site's CI and deployment contract. A Next.js
static export can use S3/CloudFront; server rendering requires a supported runtime.
